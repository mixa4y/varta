# ADR-001: System Architecture

| Metadata | Value |
|---|---|
| Status | `DRAFT` |
| Version | `v0.1` |
| Date | `2026-07-24` |

## Проблема

CSMD потребує контрольованої архітектури для роботи з чутливими документами, великими файлами, метаданими, хешами та відтворюваними перевірками. Залежність від хмарної таблиці як основного сховища ускладнює контроль оригіналів, офлайн-роботу та складні зв'язки.

## Контекст

Система повинна зберігати незмінні оригінали, працювати з кирилицею й довгими шляхами Windows, формувати аудит і не залежати від сервісу третіх сторін. Airtable раніше розглядався, але користувач прийняв рішення працювати без нього.

## Розглянуті варіанти

1. Airtable як основна база й автоматизаційний шар.
2. Локальний Python-застосунок із SQLite та файловим сховищем.
3. Серверний застосунок із PostgreSQL та об'єктним сховищем.

## Рішення

Прийняти як базову архітектуру:

- `Python` як платформу реалізації;
- `SQLite` як основну локальну базу даних;
- локальну файлову систему для бінарних об'єктів;
- незмінну зону `originals`;
- окремі зони `working`, `derived`, `reports`, `logs`;
- модульні межі `domain`, `application`, `infrastructure`, `presentation`;
- зовнішні інтеграції лише через необов'язкові адаптери.

Airtable не входить до core, не є обов'язковою залежністю та не визначає модель даних.

## Наслідки

Переваги: локальний контроль, просте резервне копіювання, офлайн-робота, відсутність vendor lock-in, атомарні транзакції SQLite.

Обмеження: багатокористувацький режим, віддалений доступ і масштабування потребуватимуть окремого ADR та, можливо, міграції на серверну БД.

## Ризики

- Пошкодження локального носія без резервної копії.
- Неконтрольований прямий доступ до `originals` поза застосунком.
- Межі SQLite при конкурентному записі.
- Різна поведінка зовнішніх криптографічних інструментів.

## Assumptions

- Початковий режим — один користувач на одному робочому місці.
- Резервне копіювання буде визначене окремою політикою.
